# Hardware Architectures and Threat Models for Protecting ML Model Weights (storage, memory, transit) — implications for an FPGA Ascon-AEAD128 (SP 800-232) weight-load layer

Scope note. Research run 2026-10-21. "Cited Findings" are statements taken from the linked source; where only an abstract or search summary was read, this is stated. "Inferences" are my deductions and are not published results. Nothing here claims novelty for this repository. The repository already documents a "safe decryption contract": decrypted bytes are tentative, are held in a quarantine buffer, and are released or discarded through `commit_o`/`discard_o` after the tag check (README.md, "Safe decryption contract"). The recommendations below build on that contract and do not replace it.

## Q1. Trust boundaries and data-path placement: what can an inline AEAD core protect for (a) at rest, (b) external DRAM/HBM, (c) PCIe/CXL/network transit, (d) a compromised compute endpoint, and where must plaintext live?

### Takeaway
An inline AEAD core protects confidentiality and integrity only for data outside the boundary formed by the key holder and the plaintext consumer. Placing the core between external DRAM and the compute fabric ("decrypt on fetch") covers cases (a), (b) and (c) with one mechanism, as long as plaintext never leaves the chip. Placing it between storage and DRAM ("decrypt on load") leaves plaintext in DRAM. That is acceptable only when DRAM is inside the trust boundary, which is how NVIDIA treats on-package HBM. In case (d), where the attacker can command the decryptor and read its output, or read plaintext on-chip, the AEAD core provides nothing. The protection then depends on command authentication, the absence of any plaintext egress path, and attestation.

### Cited Findings
- NVIDIA's H100 confidential-computing whitepaper (WP-11459-001 v1.0, July 2023) lists in-scope threats as "Software attacks, Basic physical attacks, Software Roll back attacks, Cryptographical attacks, Data Roll-back & replay attacks". It lists "Sophisticated Physical attacks" and "Denial of Service attacks" as out of scope. — [NVIDIA HCC Whitepaper v1.0](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- The same whitepaper says the on-package HBM "is considered secure against common physical attack tools, such as interposers, and is not encrypted". Plaintext therefore lives in HBM, inside the GPU package boundary. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- H100 places encryption/decryption engines "across all its ingress/egress paths", using 256-bit AES-GCM. The "bounce buffer" in shared host memory "will only contain encrypted data". The VM encrypts data into the bounce buffer, and the GPU copies it to internal memory and decrypts it there. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- H100 keys "are in keyslots which cannot be accessed by the Hypervisor", are "ephemeral", and are "lost/wiped on VM teardown or GPU reset". JTAG is disabled and BMC paths are reduced to "card health" in CC mode. Performance counters are disabled in CC-On mode because they "could be used to infer behavior" (a side-channel path). — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- MGX (ISCA 2022) assumes the TCB "mainly includes the CPU TEE and the accelerator". Internal accelerator state cannot be observed or modified physically, off-chip memory is untrusted, and "We do not consider side-channel attacks such as the memory address, timing, and power side channels". Kernels are attested and run on a trusted control processor. A DHE key exchange secures the host–accelerator channel. — [MGX, arXiv 2004.09679](https://arxiv.org/abs/2004.09679)
- GuardNN (DAC 2022) designs its instruction set so that "the TCB [is reduced] to just the accelerator". Confidentiality holds even when host-supplied instructions are untrusted. Its FPGA prototype shows about 3% inference overhead (abstract-level). — [GuardNN, arXiv 2008.11632](https://arxiv.org/abs/2008.11632)
- Graviton (OSDI 2018) isolates GPU kernels and data from the host driver, OS and hypervisor. It changes only peripheral components such as the command processor, not the GPU cores, MMU or memory controller. The reported 17–33% overhead is dominated by encryption and decryption of host↔GPU traffic (abstract-level). — [Graviton, USENIX OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/volos)
- AMD/Xilinx UltraScale devices store the bitstream-decryption key (AES-256) in BBRAM or eFUSE, and neither can be read back. The on-chip AES engine is reserved for configuration and "can't be used by user logic" (as summarized from XAPP1267). — [AMD XAPP1267](https://docs.amd.com/r/en-US/xapp1267-encryp-efuse-program/eFUSE-Programming-General-Recommendations)

### Inferences
- **Data-path option A: decrypt on fetch (core between DRAM/HBM and the accelerator compute).** The ciphertext at rest is copied unchanged into DRAM, and the same AEAD object protects storage, transit and DRAM, so (a), (b) and (c) are all covered. Plaintext exists only in on-chip buffers (BRAM/URAM, PE scratchpads). This matches the MGX, GuardNN and TNPU threat model. The cost is that weights are re-decrypted on every pass. That cost interacts with the SP 800-232 data limit (see Q4).
- **Data-path option B: decrypt on load (core between storage/PCIe and DRAM).** This protects (a) and (c) but leaves plaintext in DRAM. It is adequate only if DRAM is trusted, as NVIDIA assumes for on-package HBM. It is not adequate for discrete DDR on an FPGA board, which is open to probing and cold-boot attacks.
- **Data-path option C: transcrypt.** Verify and decrypt the storage-format object once, then re-encrypt it into DRAM under an ephemeral per-session key, with nonces generated from on-chip state. This is option B's crypto pattern applied twice. It resets the per-key data budget for every session and lets the DRAM format be tuned to the accelerator's tile size (SecureLoop/MGX granularity). It needs about twice the crypto throughput during load, plus an encrypt path.
- **Case (c), transit.** End-to-end AEAD of the weight object makes link encryption redundant for the weight payload itself. It does not protect DMA descriptors, addresses or commands. Those need either link IDE (TLP headers are integrity-protected, see Q3) or authenticated commands, as in the GuardNN instruction set.
- **Case (d), compromised endpoint.** If an untrusted host or driver can (1) issue "decrypt chunk X" and (2) read the result back, for example by DMA from an output or debug buffer, the core is a decryption oracle. Required properties: the decrypted-plaintext path must be a one-way sink into compute, with no read-back, debug, ILA or JTAG path from the plaintext buffer. The key must never be readable. Weight-dependent outputs must only leave through the intended inference result. If the attacker controls the accelerator firmware or bitstream, or can read on-chip plaintext, an AEAD layer gives no weight confidentiality. That case requires attestation of the bitstream and firmware plus bitstream encryption and authentication (XAPP1267, UG908).
- On FPGAs the hardened configuration AES cannot be reused for user data (XAPP1267). The Ascon key for user logic must therefore be (i) embedded in an encrypted and authenticated bitstream (protected by the BBRAM/eFUSE key), (ii) stored in user eFUSE bits, or (iii) delivered after attestation by key exchange. This is a deduction from the cited constraints, not a vendor recommendation.

### Gaps
- I did not verify the ARM CCA device-assignment (RME-DA) or Intel TDX Connect primary specs in this session. Their treatment of device-side plaintext and of the device as part of the TCB is therefore not cited here.
- Model extraction through query outputs (model stealing) is outside what any memory or AEAD layer can address. I collected no source on it in this run.
- HIX (ASPLOS 2019) and Telekine (NSDI 2020) were named in the assignment but not retrieved. Telekine's point that GPU kernel-launch timing leaks information is from background knowledge only and is unverified here.

## Q2. What AEAD alone cannot provide (rollback/replay, freshness, key management, nonce management, side channels, release of unverified plaintext, DoS)

### Takeaway
Ascon-AEAD128 authenticates the tuple (nonce, AD, ciphertext, tag) under a key. Nothing more. Rollback to an older validly encrypted model version, replay of a stale chunk, key provisioning and rotation, nonce uniqueness, side-channel resistance, safe early release of plaintext, and availability all need mechanisms outside the AEAD core. SP 800-232 itself imposes three operational requirements the hardware must enforce: unique nonces (R3), a decryption-failure limit (R5), and a data limit with key update (R6/R7).

### Cited Findings
- SP 800-232 R3: "Nonces shall be distinct for each encryption algorithm for a given key". R5: with a tag length λ where 64 ≤ λ ≤ 128, "the maximum number of decryption failures under a fixed key shall not exceed 2^(λ−32)". For 32 ≤ λ < 64 the limit "should" be 1 unless a careful risk analysis supports a higher one. R6: total data processed "during encryption and decryption, including the nonce, shall not exceed 2^54 bytes for a given key". R7: the key "shall be updated" at that limit and "should be updated" when the failure limit is reached. — [NIST SP 800-232 (Aug 2025), §4.3](https://doi.org/10.6028/NIST.SP.800-232)
- SP 800-232 §4.1 decryption returns P only "If the two [tags] match … Otherwise, an error message fail is returned". The specified algorithm does not release unverified plaintext. — [NIST SP 800-232](https://doi.org/10.6028/NIST.SP.800-232)
- SP 800-232 §4.4.3: confidentiality "can be compromised if a nonce or, more specifically, (nonce, associated data) pair, is reused with the same secret key". The scheme gives only "some resilience against unintentional nonce reuse". The integrity guarantees in Table 8 assume each (N, A) pair is reused at most 2^8 times. — [NIST SP 800-232](https://doi.org/10.6028/NIST.SP.800-232)
- SP 800-232 R4: truncated tags must be ≥ 32 bits, and < 64 bits only after a careful risk analysis. Tag length must stay constant over the key's lifetime. — [NIST SP 800-232](https://doi.org/10.6028/NIST.SP.800-232)
- SP 800-232 R1: keys shall be generated per SP 800-133 with an approved RBG of ≥ 128-bit strength, and "shall not be used for other purposes". — [NIST SP 800-232](https://doi.org/10.6028/NIST.SP.800-232)
- Andreeva et al. formalize "releasing unverified plaintext" (RUP), motivated by devices with too little memory to buffer the full plaintext or with real-time constraints. They define the privacy notions PA1/PA2 (plaintext awareness) and the integrity notion INT-RUP, and show that many AE schemes are insecure under RUP (ASIACRYPT 2014; abstract-level). — [IACR ePrint 2014/144](https://eprint.iacr.org/2014/144)
- Chang et al. (ToSC 2019) show that AERUP security is equivalent to conventional AE security plus plaintext awareness plus INT-RUP (abstract-level). — [IACR ePrint 2019/1326](https://eprint.iacr.org/2019/1326)
- NVIDIA counters replay on PCIe with a "rolling IV": both endpoints keep message counters, and "The receiving endpoint performing the decryption doesn't use the IV sent by the encrypting transmitter, instead it uses its own". A replayed message fails because the IV has already advanced. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- MGX: a MAC "cannot guarantee the freshness of the data". A replay attack can replace the data together with its VN and MAC, so conventional designs use a Merkle tree whose root is on-chip. — [MGX, arXiv 2004.09679](https://arxiv.org/abs/2004.09679)
- AMD lists two DPA countermeasures for bitstream decryption, "configuration counting" (BBRAM only) and "authenticate-then-decrypt" (BBRAM or eFUSE). Key rolling must always be combined with one of them. — [AMD XAPP1098](https://docs.amd.com/r/en-US/xapp1098-tamper-resist-designs/DPA-Solution-Comparison)
- AMD Bootgen "rolling keys" give each block of the boot image its own AES key, each wrapped by the previous key starting from the hardware key, to resist side-channel attacks. — [AMD UG1283](https://docs.amd.com/r/2025.2-English/ug1283-bootgen-user-guide/Rolling-Keys)
- The repository's own README states the core "is intentionally unmasked at this stage" (README.md, Architecture section). There is no first-order side-channel countermeasure.

### Inferences
- **Rollback.** A version-N ciphertext stays valid forever under the key that produced it. To prevent rollback to version N−1, either (i) derive the key or nonce from the version and refuse to derive keys for revoked versions, or (ii) bind the version into the nonce or AD and enforce `version ≥ min_version`, with `min_version` held in tamper-resistant monotonic storage (eFUSE bits, TPM NV counter, or authenticated BBRAM). AEAD alone accepts the old version.
- **Replay inside DRAM (option A).** Because weights are read-only during inference, the "version" of every weight chunk is a constant for the loaded model. That is exactly MGX's argument for a constant VN_W. If the trusted side computes the expected nonce from (model, version, tensor, chunk index) and never reads it from DRAM, replaying a different chunk or an older version fails authentication. No integrity tree is needed. This holds only when the expected identity is computed on-chip from the schedule or manifest.
- **RUP risk for weights.** Ascon's duplex mode encrypts by XORing the plaintext block with the rate part of the state, so before tag verification a flipped ciphertext bit flips the same plaintext bit in that block (later blocks become garbage). Streaming unverified plaintext into compute therefore gives a DRAM attacker targeted weight bit-flips (a fault/bit-flip-attack primitive) and, through outputs, a possible confidentiality oracle. This is a deduction from the duplex structure and the RUP framing; SP 800-232 makes no RUP claim. Chunk-level quarantine (the repository's commit/discard contract) is the conservative choice. Any "speculative compute then discard" design must guarantee that results computed on unverified weights cannot escape before the tag result.
- **DoS.** An attacker who can write DRAM or the link can always force tag failures. AEAD detects this but cannot prevent it, and NVIDIA scopes DoS out. R5 requires a hardware failure counter per key. Hitting the limit must lead to a defined state (halt or rekey), which itself is a DoS lever. Record the policy explicitly.
- **Side channels.** With an unmasked core and attacker-influenced ciphertext in DRAM, many decryptions under one key with distinct known nonces (one per chunk) give a DPA adversary varied known inputs to the initialization permutation, where the key is absorbed. This matters only if physical attackers are in scope. Mitigations by analogy to AMD: key rolling (per-tensor or per-chunk derived keys limit traces per key), a failure counter, and masking. Ascon cannot "authenticate then decrypt" the way AMD's bitstream flow does, because the tag is computed by the same key-dependent duplex that decrypts.
- **Key management** (provisioning, wrapping, attestation-gated release, per-model/version derivation) is entirely outside the core. Q5 lists the minimal set.

### Gaps
- I found no published analysis specific to Ascon-AEAD128 under RUP (INT-RUP or PA) in this session. Literature outside SP 800-232 may exist. Not verified.
- No primary source retrieved on DPA of Ascon FPGA implementations (for example CHES/TCHES papers). The side-channel inferences above are by analogy.

## Q3. Literature on accelerator/GPU TEEs and model-weight protection: crypto, granularity, and exploitation of read-only/statically known weights

### Takeaway
Published secure-accelerator designs almost all use AES-based protection: AES-CTR plus a MAC, or AES-GCM. None of the retrieved designs uses Ascon. Their main efficiency lever is the same one this repository can use. DNN memory traffic is coarse-grained and statically scheduled, and weights are read-only during inference. Version numbers can therefore be computed on-chip (often constant for weights), MACs can cover a whole tile or chunk (512 B to tensor size), and integrity trees can be dropped. Recent (2024–2026) LLM work focuses on TEE partitioning and obfuscation, and several 2026 papers show attacks on obfuscation shortcuts.

### Cited Findings
- **MGX (ISCA 2022).** Uses AES-CTR. The 128-bit counter is a 64-bit VN concatenated with a 64-bit address, with type bits distinguishing features, weights and gradients. The MAC is computed over (ciphertext ‖ PA ‖ VN). It uses "a 64-bit MAC for each 512-byte data block" to match the Xilinx CHaiDNN accelerator's 512-byte reads. "The weights are read-only during inference. Therefore, we can use a constant as the VN for the weights until they are updated". "No version number is stored in the off-chip memory, no integrity tree is needed". The baseline is Intel's MEE design: an 8-ary Merkle tree, 56-bit VNs, 64-byte granularity, and a 32 KB VN/MAC cache. A 64-bit VN would take "0.28 million years" to overflow at 1,000 inputs/s on a 1,000-layer DNN, and overflow requires re-encryption under a new key. Evaluation used SCALE-Sim and cycle-level simulation. Reported results lower average overhead from 28%/33% to 4%/5% for DNN and graph accelerators. — [MGX, arXiv 2004.09679](https://arxiv.org/abs/2004.09679); DOI 10.1145/3470496.3527418 per [NSF PAR](https://par.nsf.gov/biblio/10341709)
- **SecureLoop (MICRO 2023).** Models an AES-GCM engine (AES plus a GF multiplier). The "encryption seed is composed of a counter, the address of the data, and a randomly generated initialization vector", and the counter acts as the version number. It assumes counters "can be computed" on-chip or by the host CPU. It introduces the "AuthBlock", the unit of data covered by one hash. Prior work used "tile-as-an-AuthBlock", which causes cross-layer overhead when tilings mismatch. One fully pipelined AES-GCM engine per datatype costs about 416.7 kGates, roughly 35% of Eyeriss's logic. Its cryptography-aware scheduler, built on Timeloop, finds schedules up to 33.2% faster with 50.2% better EDP. — [SecureLoop, DOI 10.1145/3613424.3614273](https://doi.org/10.1145/3613424.3614273); [PDF](https://people.csail.mit.edu/mengjia/data/2023.MICRO.SecureLoop.pdf); [artifact](https://github.com/kyungmi-lee/SecureLoop-MICRO2023Artifact)
- **TNPU (HPCA 2022, Lee, Kim, Na, Park, Huh).** Provides "tree-less integrity protection" by exploiting DNN dataflow semantics, keeping a version number per tensor or sub-tensor inside the CPU enclave that drives the NPU. It reports single-NPU gains of 10.0% and 7.5% over a tree-based design, and 13.3% and 8.7% with three NPUs (abstract-level). — [KAIST repository, DOI 10.1109/HPCA53966.2022.00025](https://koasas.kaist.ac.kr/handle/10203/298300)
- **GuardNN (DAC 2022).** "Minimizes the overhead of memory encryption and integrity verification by customizing the off-chip memory protection for the known memory access patterns of a DNN accelerator". FPGA prototype, about 3% inference overhead. The v1 and v2 abstracts describe the integrity trade-off differently (abstract-level). — [arXiv 2008.11632](https://arxiv.org/abs/2008.11632)
- **Graviton (OSDI 2018).** GPU TEE built on command-processor changes. Overhead of 17–33% comes mainly from encrypting host↔GPU transfers (abstract-level). — [USENIX](https://www.usenix.org/conference/osdi18/presentation/volos)
- **NVIDIA H100 CC.** AES-GCM-256 on every ingress/egress path, with 96-bit IVs. The whitepaper describes (key, IV) uniqueness as limited to 2^96−1 before the key must be changed. Rolling IV counters are kept at both ends, bounce buffers hold only ciphertext, and HBM is not encrypted. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- A 2026 arXiv benchmark of Blackwell confidential computing reportedly observed AES-GCM decrypt calls of about 517 KB each, matching the bounce-buffer size. This comes from a search summary only, and the paper was not opened. — [arXiv 2608.26575](https://arxiv.org/abs/2608.26575) (unverified; treat as secondary)
- **CXL IDE** (aligned with the PCIe IDE ECN). AES-GCM with a 256-bit key, a 96-bit MAC, and TLP headers "not encrypted, only integrity protected". — [CXL Consortium IDE webinar (2023)](https://computeexpresslink.org/wp-content/uploads/2023/12/CXL_CXL-IDE-Webinar_FINAL.pdf)
- PCIe IDE IP is marketed with AES-GCM packet encryption, replay protection, TDISP support, multi-stream support and key refresh. This is a vendor claim, not the spec. — [Synopsys PCIe 5 IDE](https://www.synopsys.com/designware-ip/security-ip/interface-security-modules/security-pcie5-ide.html)
- **CryptoTensors (arXiv 2512.04580, Dec 2025).** Extends Safetensors with per-tensor AES-GCM-256 encryption. Each tensor has a random DEK and unique IV with the tag in the header. DEKs are wrapped by a master key. The header, including offsets, is signed with Ed25519, and the master key is released by a KBS after an OPA policy and attestation check. The paper does not address tensor swapping, cross-file splicing or rollback. Encrypted vLLM load time is about 8× baseline, while first-token latency stays within ±7%. — [CryptoTensors](https://arxiv.org/abs/2512.04580)
- **TZ-LLM (arXiv 2511.13717).** Protects on-device LLMs with Arm TrustZone and runs NPU acceleration within the TEE on a Rockchip device (abstract-level). — [TZ-LLM](https://arxiv.org/abs/2511.13717)
- **Amulet (arXiv 2512.07495).** Decrypts weights inside the TEE with an attestation-derived key, then obfuscates them before offloading to an untrusted GPU. Limited trusted memory forces slice-wise loading (abstract-level). — [Amulet](https://arxiv.org/abs/2512.07495)
- **TEESlice (arXiv 2411.09945).** Keeps sensitive slices in the TEE and offloads the rest (abstract-level). — [TEESlice](https://arxiv.org/abs/2411.09945)
- **Attacks on obfuscation.** One 2026 paper reports attacks on partial TEE-shielded LLM inference with precomputed noise that recover secret permutations and weights ([arXiv 2602.11088](https://arxiv.org/abs/2602.11088)). Another argues that obfuscation-based on-device LLM protections "remain largely heuristic" ([arXiv 2609.10117](https://arxiv.org/abs/2609.10117)). Both abstract-level.
- Additional related works identified but not read: TensorTEE ([arXiv 2407.08903](https://arxiv.org/abs/2407.08903)), sNPU (ISCA 2024, [PDF](https://ipads.se.sjtu.edu.cn/_media/publications/feng-isca24.pdf)), and SeDA ([arXiv 2508.18924](https://arxiv.org/abs/2508.18924)).

## Q4. Chunked/segmented AEAD for large random-access objects, and Ascon-AEAD128 nonce/data limits (how many chunks/messages per key)

### Takeaway
Use a STREAM-style construction with random access (Tink's pattern). Each chunk is an independent Ascon-AEAD128 message whose nonce is computed from (stream/model-version prefix, chunk index, last-chunk flag). Context (model ID, version, manifest hash) is bound either through key derivation or AD. Do not use libsodium-style chaining, which forbids random access. The binding constraint is not the 128-bit nonce space but SP 800-232 R6: 2^54 bytes per key, counting decryptions. If the core re-decrypts weights from DRAM on every inference pass, a single static key can be exhausted in hours to days, so per-tensor or per-session key derivation is needed.

### Cited Findings
- Hoang, Reyhanitabar, Rogaway and Vizár define OAE2 and the STREAM/CHAIN segmented constructions. They note that "nonce-reuse can still be devastating" even under OAE2 (abstract-level). — [ePrint 2015/189](https://eprint.iacr.org/2015/189)
- Tink AES-GCM-HKDF streaming: IV_i = NoncePrefix (7 random bytes) ‖ i (4-byte big-endian) ‖ b, with b = 0x00 for non-final segments and 0x01 for the final one. DerivedKey = HKDF(ikm = key, salt = random per-stream salt, info = AssociatedData). Per-segment GCM AD is empty. Any segment can be decrypted independently after reading the header. At most 2^32 segments. All segments except the last must be full. Implementations must not confuse EOF with a decryption error, or truncation becomes possible. — [Tink spec](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming)
- libsodium secretstream updates the nonce with part of the previous MAC plus a counter, uses FINAL/REKEY tags, and detects truncation, removal, reordering, duplication and modification. Decryption is sequential. — [libsodium docs](https://doc.libsodium.org/secret-key_cryptography/secretstream)
- SP 800-232: 128-bit key, nonce and tag. The data limit is 2^54 bytes per key "during encryption and decryption, including the nonce" (R6), and the key "shall be updated" at the limit (R7). Single-key strength is 128 bits with "the total number of input bytes … limited to 2^54 (i.e., 2^50 blocks)" (§4.4.1). With u keys, strength is (128 − log2 u) bits, because when "the same nonce is used with u keys, an attacker may discover one of the u keys with a time complexity of 2^(128−log2 u)". The nonce-masking option (a 256-bit key K1‖K2, nonce XOR K2) restores 128-bit multi-key strength but "should only be used when context-commitment security … and related-key security … are not concerns" (§4.2.2, §4.4.2). — [NIST SP 800-232](https://doi.org/10.6028/NIST.SP.800-232)
- MGX notes that VN overflow requires re-encryption under a new key, and that a 64-bit VN lasts 0.28 million years in its example. — [MGX](https://arxiv.org/abs/2004.09679)
- NVIDIA describes AES-GCM (key, IV) uniqueness as limited to 2^96−1 messages before the key must change. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)

### Inferences (my arithmetic, not published)
- **Nonce space is not the limit.** 128 bits easily holds 32-bit model/version + 32-bit tensor ID + 48-bit chunk index + flags. Nonce uniqueness (R3) applies to encryption. Weights are encrypted once offline per (key, version), so deterministic nonces are safe provided the same (key, nonce) is never used to encrypt different plaintext. The classic failure is re-encrypting edited weights without bumping the version or deriving a new key.
- **The data limit is the real limit when decrypting repeatedly.** 2^54 B ≈ 1.80 × 10^16 B. Per 4 KiB chunk, the input processed is about 4096 + 16 (nonce) + |AD| bytes.
  - A 70B-parameter FP16 model (about 1.4 × 10^11 B) streamed once per decode step through a decrypt-on-fetch core exhausts one key after about 1.3 × 10^5 passes. At 20 tokens/s that is about 1.8 hours.
  - A 7B INT8 model (about 7 × 10^9 B) exhausts a key after about 2.5 × 10^6 passes.
  - A 25 MB edge CNN at 1,000 inferences/s exhausts a key after about 7.2 × 10^8 inferences, about 8.3 days.
  - Under data-path option B or C (decrypt once per load or session), the same key covers about 1.3 × 10^5 full loads of a 140 GB model, which is ample.
  - Whether repeated decryption of the same valid ciphertext erodes security the way R6's proof bound assumes is a theoretical question. As written, R6 counts decryption, so a compliant design must budget for it.
- **Mitigations:**
  - (i) Per-tensor (or per-layer) derived keys, so each key's budget is tensor size × reads. With a 1 GiB tensor that is about 1.7 × 10^7 reads per key.
  - (ii) Option C transcryption into a per-session ephemeral key, which can be rotated when a hardware byte counter nears the limit. The DRAM copy is then re-encrypted, as MGX prescribes for VN overflow.
  - (iii) A hardware 64-bit "bytes processed under current key" counter that enforces R6/R7.
- **Multi-key cost of derived keys.** u = 2^10 per-tensor keys costs up to 10 bits (118-bit strength) under SP 800-232's same-nonce multi-key attack. If nonces are globally unique across derived keys (nonce includes tensor ID and chunk index), the cited attack premise ("same nonce … with u keys") does not arise. This is my reading, not an SP statement. Alternatively use nonce masking, but that sacrifices context commitment, which matters if the same ciphertext must not decrypt validly under two contexts.
- **Chunk-size trade-off for Ascon-AEAD128** (approximate, from the algorithm structure: p^12 init, p^8 per 16-byte AD/data block, p^12 finalization). Per-chunk fixed cost is about 24 rounds plus 8 × ⌈(|AD|+1)/16⌉ rounds if AD is non-empty. Payload costs 8 rounds per 16 bytes.
  - 4 KiB chunk: about 2,048 payload rounds versus about 24–48 fixed, so 1–2% crypto overhead. The 16-byte tag is 0.39% storage overhead.
  - 512 B chunk (MGX/CHaiDNN granularity): about 256 versus 24–48 rounds (9–19%), and a 3.1% tag overhead.
  - 64 B chunk (cache line): about 32 versus 24–48 rounds (75–150%), and a 25% tag overhead.
  - Moving context out of per-chunk AD and into key derivation or the nonce (Tink's "AD as HKDF info, empty per-segment AD") removes the AD rounds entirely.
  - These figures should be checked against the repository's buffered three-round datapath.
- **Quarantine buffer** = one chunk (4 KiB fits easily in BRAM). Double-buffering hides tag latency, because chunk i+1 decrypts while chunk i waits for the commit/discard decision.

- The age file format's STREAM variant (ChaCha20-Poly1305, 64 KiB chunks) was not retrieved in this session.

- Hoang & Shen's multi-user Tink bounds (ePrint 2020/1019) were not read in detail.

## Q5. Manifest binding of tensor identity, order and address, and the minimal additional components (monotonic counter, key store, attestation, manifest MAC)

### Takeaway
The trusted side must derive each chunk's expected identity (model ID, version, tensor ID, chunk index, last flag, length) from an authenticated manifest and the accelerator's own schedule. It must never derive that identity from bytes fetched next to the ciphertext. Binding these into the nonce, AD or key prevents reordering, splicing across tensors, models or versions, and truncation. Rollback additionally needs a monotonic minimum-version in tamper-resistant storage. The minimal component set is: a protected root key (eFUSE/BBRAM or bitstream-embedded), a KDF, an authenticated manifest, a monotonic counter, the tag-failure and byte counters required by SP 800-232, and an attestation or key-release path if keys are delivered remotely.

### Cited Findings
- MGX counters include the memory address, so "using one VN for multiple memory locations does not sacrifice security because the counter value includes a memory address". VNs are "kept as part of the program state in the trusted control processor". — [MGX](https://arxiv.org/abs/2004.09679)
- SecureLoop's encryption seed is counter ‖ address ‖ random IV. — [SecureLoop](https://people.csail.mit.edu/mengjia/data/2023.MICRO.SecureLoop.pdf)
- Tink binds the caller's AD by using it as HKDF `info` when deriving the per-stream key. It binds order with the segment index in the IV and truncation with the last-segment flag. — [Tink spec](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming)
- CryptoTensors signs all header metadata and offsets, verifying the signature before decryption, but "does not address" tensor swapping, cross-file splicing or rollback. — [CryptoTensors](https://arxiv.org/abs/2512.04580)
- NVIDIA lists "Software Roll back attacks" and "Data Roll-back & replay attacks" as in scope and uses receiver-maintained IV counters for channel replay. — [NVIDIA HCC Whitepaper](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf)
- AMD UltraScale keys reside in BBRAM or eFUSE and cannot be read back. Configuration counting, a DPA countermeasure, works only with BBRAM. Downloading a BBRAM-encrypted bitstream before the key is loaded can lock the device until power-cycle. — [XAPP1267](https://docs.amd.com/r/en-US/xapp1267-encryp-efuse-program/eFUSE-Programming-General-Recommendations); [XAPP1098](https://docs.amd.com/r/en-US/xapp1098-tamper-resist-designs/DPA-Solution-Comparison); [UG908](https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging/Generating-Encrypted-and-Authenticated-Files-for-UltraScale-and-UltraScale)
- SP 800-232 nonce masking is not context-committing: two different (K2, N) pairs with equal N ⊕ K2 produce the same (C, T). — [SP 800-232 §4.2.2](https://doi.org/10.6028/NIST.SP.800-232)

### Inferences
- **Recommended binding (deduction).** Manifest M = {model_id, version, per-tensor: tensor_id, dtype, shape, byte_length, chunk_count, DRAM/base offset}. It is authenticated as a whole, either by an Ascon-AEAD128 tag with empty plaintext and AD = M under a manifest key, or by a signature verified by a boot processor. h = Hash(M), for example Ascon-Hash256.
  - K_mv = KDF(K_root, "weights" ‖ model_id ‖ version ‖ h).
  - Optionally K_t = KDF(K_mv, tensor_id), for the data limit (Q4).
  - Nonce_i = domain(8b) ‖ tensor_id(32b) ‖ chunk_index(48b) ‖ last_flag(8b) ‖ reserved/zero(32b).
  - AD = empty, or a small fixed header such as dtype and length if not already bound through h.
  - Effect: swapping chunks within a tensor changes the index, so it fails. Moving a chunk to another tensor changes the tensor_id, so it fails. Mixing in chunks from another model or version changes the key, so it fails. Truncating a tensor fails because the last_flag and the chunk_count from M are enforced. Presenting an old full model version authenticates (old key, old manifest). Only the min-version check stops it.
- Physical-address binding (as in MGX) is needed only if the fetch engine's notion of "which chunk" comes from the untrusted address map. If the trusted scheduler requests (tensor, chunk) and computes the nonce itself, logical identity suffices.
- An attacker who can rewrite the manifest in storage must not be able to change h without detection. The manifest must therefore be authenticated by a key or signature the attacker lacks. h then commits the whole model layout through key derivation.

### Design Requirements (derived; each tagged with the motivating source)
- **REQ-B1 (identity from trusted state).** The decryptor computes nonce, AD and expected length from the authenticated manifest and on-chip schedule state. It never uses nonce or identity fields read from untrusted memory as authoritative. [MGX, TNPU, NVIDIA receiver-side IV]
- **REQ-C1 (STREAM-style chunks).** Each chunk is an independent Ascon-AEAD128 message. Nonce = domain ‖ tensor_id ‖ chunk_index ‖ last_flag (128 bits). This gives random access. [STREAM, Tink]
- **REQ-C2 (truncation).** Enforce chunk_count and byte_length from the manifest. A missing final chunk is an error, distinct from end-of-data. [Tink EOF warning]
- **REQ-C3 (no chaining).** Do not chain nonces through prior MACs (libsodium style), because random access to weights is required. [libsodium]
- **REQ-K1 (root key storage).** The root key is held in non-readable storage: BBRAM/eFUSE-protected encrypted bitstream, or user eFUSE. It is never exposed on any readable register, ILA or JTAG path. [XAPP1267, NVIDIA keyslots]
- **REQ-K2 (derivation).** Derive per-model-version keys bound to the manifest hash, optionally per tensor. Keys "shall not be used for other purposes" (R1), so use separate derived keys for the manifest MAC and for weight chunks. [SP 800-232 R1, Tink HKDF-info]
- **REQ-N1 (nonce uniqueness).** The offline encryptor must refuse to encrypt under an existing (key, version) whose content changed. A version bump means a new key. [SP 800-232 R3]
- **REQ-N2 (data budget).** Keep a hardware 64-bit counter of bytes processed (including nonces) per active key. Rekey, re-derive or transcrypt before 2^54. Size the key granularity to the re-read rate (Q4 arithmetic). [SP 800-232 R6/R7]
- **REQ-N3 (failure budget).** Keep a per-key decryption-failure counter. With 128-bit tags, the hard ceiling is 2^96. Define a policy to halt, alert or rekey well below it. Keep tag length fixed at 128 bits unless a documented risk analysis justifies truncation (≥ 32, < 64 only with analysis). [SP 800-232 R4/R5]
- **REQ-N4 (multi-key).** Keep nonces globally unique across derived keys, or document the (128 − log2 u)-bit strength. Use nonce masking only if context commitment is not required. [SP 800-232 §4.2.2, §4.4.2]
- **REQ-R1 (no unverified release).** Plaintext of a chunk is released to compute only after its tag verifies (the repository's existing commit/discard quarantine). If speculative compute is ever allowed, no result derived from unverified chunks may leave the chip before verification. [SP 800-232 §4.1 decrypt semantics, RUP literature]
- **REQ-V1 (rollback).** Keep a monotonic min_version in eFUSE, BBRAM or an external TPM NV counter, and reject manifests with version < min_version. The anti-rollback update must be authenticated. [NVIDIA rollback in scope; AEAD cannot prevent]
- **REQ-D1 (endpoint isolation).** No read-back path from plaintext weight buffers to the host or debug. Accelerator commands are authenticated or constrained so that untrusted software cannot turn the core into a decryption oracle. Debug, ILA and JTAG are disabled or excluded in secure mode. [GuardNN, Graviton, NVIDIA JTAG/perf-counter lockout]
- **REQ-A1 (attestation and key release).** If keys come from a remote owner, release them only after attestation of the bitstream/firmware hash and the manifest hash (KBS-style). [CryptoTensors KBS flow, Amulet, MGX attestation]
- **REQ-G1 (granularity).** Chunk size = accelerator fetch tile (≥ 512 B, preferably 4 KiB or more for Ascon fixed-cost amortization). Avoid AuthBlock/tile mismatch. [MGX, SecureLoop]
- **REQ-G2 (throughput accounting).** Include AEAD throughput and tag latency in the accelerator schedule. A crypto engine with too little throughput becomes the bottleneck. [SecureLoop]
- **REQ-S1 (side channels, if physical attackers are in scope).** Masking or hiding, plus key rolling (per-tensor keys), plus failure counting. Otherwise, document side channels as out of scope, as MGX and NVIDIA do for sophisticated physical attacks. [XAPP1098, UG1283, repository README "unmasked"]
- **REQ-DoS.** Document that tamper causes fail-stop (detected, not prevented). Availability is out of scope. [NVIDIA]

### Gaps
- The PCI-SIG TDISP and IDE primary specifications (key refresh rules, TLP counter layout, device-interface locking) were not retrieved. Any statement about how a TDISP-assigned FPGA device would expose this core to a CVM is unverified.
- Whether an FPGA board such as the repository's Nexys A7 (Artix-7) offers user-accessible eFUSE or BBRAM, and what bitstream encryption mode 7-series uses, was not verified in this session. XAPP1267 covers UltraScale.

## Q6. Memory encryption engines (Intel MEE/SGX, TME/MKTME, AMD SME/SEV-SNP) as comparison points: overheads, counter caching, and what is unnecessary for read-only weights

### Takeaway
General-purpose memory encryption engines must handle arbitrary writes at cache-line granularity. Freshness then requires per-line version counters plus an integrity tree with an on-chip root (SGX MEE), or confidentiality without cryptographic integrity (TME/SME-class engines; not verified here). For read-only, statically scheduled weights, the counters, the tree and the counter cache are all unnecessary. A constant (per-version) VN and coarse-grained MACs suffice, and MGX quantifies the saving.

### Cited Findings
- Intel SGX's MEE protects "confidentiality, integrity, and freshness" of CPU–DRAM traffic over a protected range, using an integrity tree that mostly resides in DRAM with only a small internally stored root (abstract-level). — [Gueron, ePrint 2016/204](https://eprint.iacr.org/2016/204)
- MGX's MEE-like baseline uses a "multi-level 8-ary Merkle tree with 56-bit VNs and MACs" at "64-byte granularity" with a 32 KB VN/MAC cache. "Because the DNN accelerator has a largely streaming memory access pattern, increasing the VN/MAC cache does not help unless it is big enough to capture temporal locality across layers". Memory-traffic overhead of the baseline reached 49.2% in the worst case (as summarized in MGX's motivation). MGX reduces average overhead from 28%/33% to 4%/5% (DNN/graph). — [MGX](https://arxiv.org/abs/2004.09679)
- MGX: "Intel SGX uses a 56-bit VN". For read-only data, MGX uses a constant VN and needs no tree. — [MGX](https://arxiv.org/abs/2004.09679)
- TNPU removes the integrity tree by keeping per-tensor version numbers in an enclave, improving on tree-based designs by 7.5–13.3% (abstract-level). — [TNPU](https://koasas.kaist.ac.kr/handle/10203/298300)
- SecureLoop: one AES-GCM engine per datatype costs about 416.7 kGates (about 35% of Eyeriss's logic), so crypto-engine area and throughput are first-order costs on low-power accelerators. — [SecureLoop](https://people.csail.mit.edu/mengjia/data/2023.MICRO.SecureLoop.pdf)

### Inferences
- For a weight-only, read-only stream, the following are unnecessary: per-line VN storage, VN/MAC caches, integrity trees, write-back re-encryption, and counter-overflow handling during a model's lifetime. Still required: replay and splice protection (identity bound into the nonce), rollback protection at model-version granularity (min_version), and the per-key data and failure budgets.
- Activations, KV caches and gradients are written. If the same core later protects them, MGX/TNPU-style computed VNs come back into play (an output-feature VN incremented per layer or per inference), and per-write nonce uniqueness becomes a live concern. This is out of scope for a weight-only path, but it is the obvious next boundary.

### Gaps
- No primary sources on Intel TME/MKTME (AES-XTS) or AMD SME/SEV-SNP (AES with an address tweak; RMP-based rather than cryptographic integrity) were retrieved in this session. Those characterizations are from background knowledge and must be verified against the Intel and AMD whitepapers before citing.
- No measured latency or bandwidth figures for TME, SEV or MKTME were collected. ARM MTE is a tagging mechanism, not encryption, and was deliberately excluded per the assignment.
